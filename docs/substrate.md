# Agent Substrate workspace

A view over [Agent Substrate](https://github.com/agent-substrate/substrate): which actors are not running as they should, why, and whether the workers and pools have room for them. Substrate keeps actors, actor templates, workers and atespaces in its own API server (PostgreSQL behind gRPC), not in Kubernetes. Kubernetes holds only the WorkerPools, their worker Pods and the SandboxConfigs. The workspace joins the two, and says which side each value came from. The per-kind readings it builds on (WorkerPool status, Issues, charts) are described in [integrations.md](integrations.md#agent-runtimes-agent-sandbox-and-agent-substrate).

Reading never writes. Radar does not create, suspend, resume or delete actors.

## Code boundaries

- `pkg/substrate` is the read model and every derivation: actor rows, resume source, pool joins and capacity, template rows, eligible pools, log filtering and the needs-attention rules. It is pure (no gRPC, no `internal/` imports), so Radar Hub can reuse it. Its types are also the wire shapes of `/api/substrate/*`. What an omitted field means depends on the field: an omitted object or measurement is unknown, never zero; an omitted list or map on something Substrate returned is empty (no snapshots; a selector that matches every pool); an omitted boolean is false; and a list a response builds from reads is `[]` when read and empty, absent when not read.
- `internal/substrate` is the client: the connection settings store, the dial (port-forward or endpoint, TLS, tokens), one shared fleet snapshot and point reads, conversion from Substrate's API types, and error codes. It imports Substrate's published v1 API from `go.ate.dev/substrate/api/ateapi/v1`.

  **Updating the Substrate API**

  The API package lives in Substrate's server module, so `go get go.ate.dev/substrate@<version>` resolves the whole module's requirements. Check `git diff go.mod` after the bump and reject it if any other direct dependency changes version or if the bump introduces a new major version into `go.mod`. Then run `go test ./internal/substrate/... ./scripts/substrate-demo/fakeapi` and `go test ./internal/server -run Substrate`.

- `internal/server/substrate_workspace_handlers.go` serves the routes and decides who may read what ([API](#api)).
- `web/src/api/substrateWorkspace.ts` holds fetching and wire types; `web/src/components/substrate/` the screens. `host.tsx` composes the WorkerPool kind into Radar's generic views; `workspaceRoute.ts` the route metadata.

## Where it lives

When the `ate.dev` CRDs are discovered, the Resources sidebar's **Integrations** block lists Substrate as **Agent actors**, with "Agent Substrate" beneath and a badge counting non-informational fleet findings. One finding can group many actors. Each destination’s badge counts the objects its own **Needs attention** filter includes. The Actors filter covers reported crashes, unavailable or restarted workers, and stuck transitions. The Templates filter covers failed golden starts, selectors that match no pool, and templates with actors in the Actors filter. Opened, it lists these destinations; SandboxConfig and CSIDriverConfig stay under **Other kinds**.

| Destination | Route | Answers |
|---|---|---|
| Overview | `/substrate` | **Needs attention** leads with the strongest findings and folds remedies and commands under Details. **At a glance** covers actors, worker capacity, template startup, snapshot uploads and Prometheus delivery metrics. Coverage, connection and atespace inventory share a disclosure |
| Actors | `/substrate/actors` | Reported phase distribution and a separate **Needs attention** filter. Filter by atespace, template, pool, worker or name. Counts cover the filtered read before paging |
| Templates | `/substrate/templates` | Startup snapshots, actors needing attention, label-matched pools and per-actor resources. Blocked and failed starts sort first |
| Workers | `/substrate/workers` | Substrate workers and Kubernetes Pod readiness. Expand assigned actors or open the Pod. The Pod shows a Substrate context card with links back to the pool and the assignments |
| Pools | `/resources/workerpools?apiGroup=ate.dev` | Compare workers accepting actors, slots on active workers, Kubernetes readiness and the strongest finding. Pools named only by Substrate link to their worker inventory |

Badges leave out `info` rows (a drain still within its deadline). A badge whose rules could not be evaluated, because their inputs were not read, reads as a lower bound (≥N), and its zero as unknown.

**Pages.**

| Page | Route | Holds |
|---|---|---|
| Actor | `/substrate/actors/<atespace>/<name>` | Overview shows the leading problem, current-template recovery and the recommended move, placement, recent logs and outbound policy. Recovery steps show the target and consequences before commands. Snapshots leads with the recorded resume source. Logs distinguishes an unread source from zero matches and offers an external query when worker logs are gone. Egress and Spec show the policy and the recorded configuration |
| Template | `/substrate/templates/<atespace>/<name>` | Overview shows startup, placement and actor findings. Configuration is folded there and available in Spec. Environment values are redacted when secret-shaped |
| WorkerPool | `/substrate/workerpools/<namespace>/<name>` | Overview separates desired replicas, controller report, observed Pods and Substrate registrations. It keeps the placement grid for registered workers, template matches, metrics availability and folded sandbox class conditions. Workers links an empty registry back to the cause. Spec & status groups desired, reported and condition evidence |

## Navigation

- **Two drawers.** Kubernetes objects (WorkerPools, worker Pods, Nodes) open in the app's resource drawer (`?drawer=`). Actors are not Kubernetes objects: they open in Substrate's own drawer (`?actor=<atespace>/<name>`), which shows the actor page's Overview with **Open actor**, **Snapshots** and **Logs**. One drawer is open at a time.
- **Links.** A Needs attention row links to the recorded object or to a filtered inventory. **View all crashed actors** includes failed golden builders, whose recovery is tracked on their templates. **View all suspended actors** opens the broader phase for an overdue-upload finding.
- **Context.** Page URLs carry `ctx=<kube context>`, kept across a context switch, so an actor of the same name in another cluster never opens.
- **Namespace filter.** It does not apply: actors live in atespaces, which are Substrate's tenancy, not namespaces. The header's picker is disabled with a tooltip on every Substrate screen and on the Pools list. The Actors screen has an Atespace filter instead.

## Three sources

The Overview’s coverage and connection disclosure and the lists name their sources: Substrate's API (connected or why not, who Radar reads as, the endpoint, how old the read is), Prometheus (connected or not), and Kubernetes (always).

| Source | What it holds | Read as | Where |
|---|---|---|---|
| Kubernetes | WorkerPools (desired and ready workers, sandbox classes, Radar's WorkerPool verdict), worker Pod readiness, Node readiness | WorkerPools as the caller, through the workspace coverage machinery; Nodes only when the caller may list them; Pod readiness from Radar's cache, shown only beside the API's workers | Everywhere Radar runs |
| Substrate's API | Actors, templates, workers, atespaces, an actor's egress policy | Saved local identity, or ate-client minted with each signed-in caller's own access ([Connecting](#connecting-to-substrates-api)) | Private local Radar, or signed-in callers whose own Kubernetes access can mint `ate-client` |
| Prometheus | Charts and hourly facts on the WorkerPool and Node pages | Radar's Prometheus connection | Wherever Prometheus is connected ([integrations.md](integrations.md#agent-runtimes-agent-sandbox-and-agent-substrate)) |

Without the API, the workspace still shows pools from Kubernetes ("3 ready of 5, worker Pods, from Kubernetes"), says actors, templates and workers are kept in Substrate's API, and offers to connect when this Radar can.

### Where each value comes from

| Value | Source | When it can't be read |
|---|---|---|
| Actor state, template, assignment (worker, pool, Pod, node, epoch), crash message and time, snapshots | `ListActors` in the shared read; `GetActor`, fresh, on an actor's page and drawer | "Not connected" with the reason. A partial read (atespaces denied, read only through the settings' scope, or the cap reached) says so, and counts over it are lower bounds |
| How long a state has held | The actor's or worker's last update time. Substrate records no transition time, but every state change updates the object, so this is a lower bound: "at least 12m". A worker row's `heldForSeconds` is absent when Substrate reports no update time | Absent when Substrate reports no update time |
| What a resume restores (`resumesWith`, `resumeCondition`) | The newest snapshot with local files or a completed durable copy. Filesystem or volumes by its fidelity (a `rootfs` snapshot restores the filesystem); volumes only when it was captured under a template UID the actor no longer runs. A `memory` snapshot is qualified by runtime, as Substrate decides it: Substrate restores memory only on a worker whose runtime can restore the snapshot (same class and schema, matching attributes, CPU features a subset of the worker's), and otherwise places the actor on another runtime of the class and restores the filesystem. So a resuming actor reads `memory` or `filesystem` with `runtimeMismatch` from the worker it was placed on; otherwise it reads `filesystem` with `runtimeMismatch` for an unpinned actor when the complete worker list has active workers of its class matching both the template selector and the actor selector, and none of those runtimes is compatible. Other memory restores remain conditional (`compatibleRuntime`) | `unknown` when the template's UID was not read, or the snapshot names no fidelity. With incomplete worker coverage or no known matching worker, a memory snapshot reads `memory` with `compatibleRuntime` |
| Golden snapshot | The template's golden status: ready (with its tag), failed (terminal, with Substrate's message), building, or disabled. A building snapshot that no pool can run reads `blocked: noMatchingPool`: Substrate retries it without end and never fails it | The template list was not read |
| Pools that can run a template (`matchingPools`) | Substrate's equality-only worker selector against every pool Radar knows: WorkerPools' labels, else the labels Substrate copies onto that pool's workers. An empty selector matches every pool | `[]` (none) only with `matchingPoolsComplete`, when every WorkerPool was read. `null` when Radar cannot say: no pool list was read, or none of a partial list matches. Otherwise the pools found, which on a partial list may not be all |
| Worker state, capacity, allocated, epochs, sandbox classes | `ListWorkers` | "Not connected" or the coverage reason |
| A free actor slot on a worker (`hasFreeSlot`) | Actors allocated below the worker's actor capacity, the dimension Substrate's own capacity metrics count. Substrate treats an unreported dimension as zero, so no capacity is no slot. A free slot does not mean a given actor fits: placement also books its CPU and memory, runtime overhead included | — |
| A pool's capacity verdict (`capacity`) | `short`: fewer workers take actors than the pool wants. `full`: no active worker has a free slot. `noRoom`: active workers have free slots, but none can fit a fresh actor of any template matching their live worker labels. Radar compares the CPU and memory the worker has left against the template limits plus the worker's default runtime memory overhead, including fixed overhead on a zero-limit template. `lacking` names the dimensions that bind. `free`: some active worker has a free slot | `noRoom` needs every worker and every template read and a template that matches a worker with a free slot. A free slot can fit one template while another template needs more resources. Resume placement can also depend on snapshot locality and runtime |
| Worker Pod Ready | Radar's Pod cache, in namespaces where the caller may list Pods | Absent when the Pod is not cached, or the caller may not list Pods in its namespace |
| WorkerPool desired, reported readiness, observed readiness and finding | `spec.replicas`, `status.readyReplicas`, Pods observed by Radar, and the pool’s shared finding | Unreported replica counts remain unreported. Pod counts require `list pods` and collected Pods. Pool inventory requires `list workerpools.ate.dev` |
| Node Ready (for the upload rule) | Radar's Node cache, when the caller may list Nodes | The node's state is unknown, and the row does not escalate on it |
| Atespaces | `ListAtespaces`, else the settings' scoped atespaces. Each row says how much of its actors and templates was read (`actorsRead`, `templatesRead`: `full`, `partial`, `denied` or `unread`), with counts only when full or partial | The list is absent when atespaces were neither listed nor scoped; atespaces outside the scope stay unknown |
| An actor's log lines | The assigned worker Pod's log (`origin: worker`), filtered to the actor's container output, lifecycle events and worker records. An actor without a worker is searched for in up to 6 Pods on its last node (`origin: lastNode`). Each line and `memoryKill` evidence name their source Pod and namespace. Each Pod search requests up to 20,000 lines and 8 MiB, then tries a shorter tail once if the byte cap would cut off the newest lines. A Pod can use up to 16 MiB of reads across the two requests. The Overview preview polls assigned-worker logs and reads last-node logs on open, a phase or worker change, or refresh | A last-node search with zero readable streams after attempting a read returns 502 `logsUnavailable`. `noMatch` means at least one log was read and none of the logs read had a match. `partial` means other logs could not be searched; `windowFull` means a scan reached its line or byte limit |
| Egress | `GetActorEgressPolicy`: the rules' destinations, not the whole policy | With no policy, or one with no rules, it says Substrate denies all outbound traffic, as its egress gateway does; the error when the read failed |

The newest logged memory-limit kill attempt is returned as `memoryKill`. `current` requires Substrate's recorded memory-limit crash, a log timestamp within 10 minutes before the crash, no execution start or restore in between, and no later failed kill record for the actor. Only a tied kill supplies the template-move and revert steps. Other attempts remain log evidence.

**Coverage and budgets.** Each API kind carries a coverage: `full` (every page of every scope read), `partial`, `denied` or `failed`, with a `code` unless full (`denied`, `scoped`, `capExceeded`, `unreachable`, `unauthenticated`, `failed`). A snapshot reads at most 50,000 actors and 10,000 of each other kind, across every atespace, in pages of 1,000. Past that budget the kind is partial with code `capExceeded`, holds what was read, and names the atespaces the budget left unread in `unreadAtespaces`, never a silent truncation. Separate atespace reads share a 50,000-actor budget across cached and in-flight reads and claim space as they retain actors. One atespace can use the full budget when available. If no budget remains, the requested atespace is reported unread with partial coverage and `capExceeded`. Read atespace by atespace, coverage also names `readAtespaces` and `deniedAtespaces`. A read's pages are not one point in time: an actor created or deleted during it may be missed, and Radar keeps the newest entry it saw for each actor.

**Freshness.** One read of every kind serves all requests for 5 seconds after it completes. After that, a request starts a new read and, while it runs, is answered from the last good read for up to 2 minutes after that read completed: the tier says `refreshing: true`, and `lastError` (`code`, `message`, `at`) when the newest read failed. A read with no usable kind and at least one failed kind fails the tier with code `failed`. Past 2 minutes a failed read is the answer. `readStartedAt` and `readAt` bound the read the counts come from. With nothing usable, a request waits for the read, except `/status`, which answers `connecting`, and actor detail and logs, which read the actor directly. Actor detail enriches the fresh actor from an existing snapshot when available and otherwise reads its template and assigned worker by point lookup. It also refreshes the assigned worker by point lookup when the snapshot is older than five seconds. Its coverage describes any missing fleet reads. A context switch or a settings save discards every read and cancels any still running under the old connection.

## Connecting to Substrate's API

**Who reads the API.** Substrate authorizes by its own roles. Radar reads it only as an identity the requesting person could use themselves:

- **Private local Radar** (CLI or Desktop, authentication off, loopback listener): the identity saved in **Settings → Agent Substrate** for this kube context.
- **Signed-in OSS Radar and Radar Hub:** every signed-in person whose own Kubernetes client can create a token for `ate-system/ate-client`. This includes Hub owners, members and viewers; the Cloud role does not decide this access. Radar uses their impersonated access (proxy/OIDC) or their own Kubernetes token (user-token mode), never a ServiceAccount fallback. A request with no user or no usable user client is refused with `mintDenied`. In user-token mode, a non-system user must include a Kubernetes token on every request, including reads with a recent proof. Radar refuses requests without one before consulting the cache.
- **Shared Radar without sign-in**, including Docker, in-cluster and local non-loopback listeners: disabled with `sharedRadar` before any saved file, mint, dial or API cache is accessed. Sign-in lets Radar establish who is asking. Port-forwarding a shared Pod does not make it private local Radar.
- **Operator off switch:** `substrate.api.enabled=false` (`RADAR_SUBSTRATE_API=disabled`) disables managed API reads for everyone with `apiDisabled`. Private local settings are independent of installation configuration.

Signed-in reads use `sharedAsCaller`, the principal `system:serviceaccount:ate-system:ate-client`. Each caller proves their own access with a TokenRequest (audience `api.ate-system.svc`, one-hour lifetime) before any warm-cache read. A successful proof lasts at most 50 minutes; another person's proof never authorizes the caller. A TokenRequest refused with Kubernetes 401 or 403 gets `mintDenied` even while another user's snapshot is warm. The token and proofs are retired on context changes. Reads share one connection and one token. Warm callers can read while another caller mints. If Substrate rejects the shared token, Radar drops it and the next signed-in request mints a fresh one. Background refreshes never mint. During normal operation this creates roughly one TokenRequest per active person per hour in Kubernetes audit logs. Repeated rejections can increase this frequency. The token is never logged or returned. `ate-client` is usually a global owner in Substrate; Radar calls only its read RPCs, pinned by `TestRadarCallsOnlyReadRPCs`.


Kubernetes's built-in `edit` role includes `create serviceaccounts/token`, and
`admin` inherits it. With Radar Hub's default role bindings, members and owners
therefore already qualify wherever those bindings cover `ate-system`; a
separate Role is needed only for people without that existing grant. The default
`view` role does not grant token creation. Operators can disable the integration
with `substrate.api.enabled=false`. Check the intended person's actual access:

```bash
kubectl auth can-i create serviceaccounts/ate-client --subresource=token \
  -n ate-system --as=alice --as-group=radar:member --as-group=system:authenticated
```

**Managed installation.** The operator configures OSS and Hub agents through Helm values, or environment variables, then rolls out Radar. Settings shows effective values and the requesting person's own access outcome; it never writes installation settings. No operator token Secret is supported and the chart adds no permission for Radar's ServiceAccount to mint tokens. See the [chart's Substrate settings and caller Role](../deploy/helm/radar/README.md#agent-substrate-api).

| Helm value | Environment | Default |
|---|---|---|
| `substrate.api.enabled` | `RADAR_SUBSTRATE_API` (`enabled` or `disabled`) | `true` / `enabled` |
| `substrate.api.endpoint` | `RADAR_SUBSTRATE_ENDPOINT` | `api.ate-system.svc:443`, direct dial |
| `substrate.api.serverName` | `RADAR_SUBSTRATE_SERVER_NAME` | `api.ate-system.svc` |
| `substrate.api.caConfigMap` (`name`, `key`, default `ca.crt`) | `RADAR_SUBSTRATE_CA_FILE`, a PEM path mounted read-only | Live ClusterTrustBundle |
| `substrate.api.atespaces` | `RADAR_SUBSTRATE_ATESPACES`, comma list | `[]`; fallback only if listing is denied, at most 64 unique DNS-1123 labels |

Explicit invalid environment values are logged and keep the managed API visibly failed with `invalidSettings`; Radar never silently substitutes defaults. Managed GET responses name the trust source (`clusterTrustBundle` or `caFile`), never its path, and include atespaces only after this caller is connected.

**Identity.** **Settings → Agent Substrate** asks who Radar reads Substrate as. The section appears only for a cluster that serves Substrate's API (`ate.dev`), or one that still has a saved connection, so it can be disconnected:

- **Shared** (`shared`): Radar mints tokens for `ate-system/ate-client`, as `kubectl ate` does without `--token-file` (audience `api.ate-system.svc`, one hour, re-minted 10 minutes before expiry). Everyone who can create a token for that ServiceAccount is the same principal, `system:serviceaccount:ate-system:ate-client`. Minting needs `create serviceaccounts/token` in `ate-system`.
- **Token file** (`tokenFile`): Radar sends the bearer token in a local file, read on every call, so a rotated token is picked up without reconnecting. Substrate does not say who a token authenticates as, so the source line names only "a token file".
- **Atespaces** (optional): for a token that may read some atespaces but not list them. Radar reads the named atespaces (up to 64) one by one; the rest stay unknown. When Substrate lists atespaces, the list is ignored.

When Substrate denies a list across atespaces, Radar lists the atespaces it may see and reads each one, eight at a time. Atespaces it is refused are named in the coverage, and the kind is partial with code `denied`.

**Local endpoint.** By default a private local Radar port-forwards to Service `ate-system/api` port 443 (resolving a named target port as kubectl does), and checks the server's certificate against the cluster's live ClusterTrustBundles for Substrate's signer (`servicedns.podcert.ate.dev/identity`, label `podcert.ate.dev/canarying=live`) and the name `api.ate-system.svc`. Under **Advanced**:

- **Endpoint** (`host:port`) dials directly instead of port-forwarding.
- **CA file** (PEM) verifies the endpoint instead of the trust bundles.
- **Server name** overrides the TLS name checked.

CA file and server name apply only with an endpoint. Connections use TLS 1.3, and the token is sent only after the handshake verifies the server. Error text never carries the token.

**Where settings live.** `~/.radar/substrate.json`, next to `clusters.json`, keyed by the kube context's binding. It holds paths, never a token. Each entry records the Kubernetes target fingerprint and `config.TargetIdentity`. A changed target pauses the connection (`targetChanged`) until the person reviews the current target and uses `action: "reconfirm"`, or disconnects. Saves carry a content revision; a concurrent CLI/Desktop save or hand edit gets 409 `conflict`. File changes and context switches retire the manager generation before another cache read. Changing endpoint, CA file or server name while retaining the same identity and token path requires `confirmDestination: true` (otherwise 409 `confirmDestination`) before any probe sends a credential. A context with no entry is `notConfigured`. See [configuration.md](configuration.md#agent-substrate-connection).

**Connection states.** The API tier is `connected` (a snapshot or the actor detail was read; `refreshing` and `lastError` say when it is an older one served while a refresh runs or after one failed), `connecting` (settings saved, first read still running; `/status` never waits for it), `notConfigured` (code `notConfigured`), `disabled` (no sign-in: `sharedRadar`; operator off: `apiDisabled`), or `failed` with a code: `targetChanged`, `contextChanged` (the context or settings changed during the read; safe to retry), `notInstalled` (no Service `ate-system/api`), `tls`, `unreachable`, `unauthenticated`, `settingsFile` (`~/.radar/substrate.json` unreadable), `mintDenied`, `invalidSettings` or `failed`. `connected` and `connecting` carry no code.

## Needs attention

`pkg/substrate.NeedsAttention` applies every rule to one read. A rule runs only when the lists it needs were read, at least in part; a rule whose inputs were not read is skipped, never read as "none". The workspace also returns `checks`, each rule with whether it ran and why not (`collecting` when it waits only on Radar's first collection from a connected Prometheus, which a later read has; the Overview says those are still running, not that they could not run), and `notAssessed`, the health surfaces no rule reads (API operation errors, resumes that fail before placement, request routing and egress, worker log collection), so an empty list says what was checked.

Severities follow the house's four steps: `critical` (something is already lost or down), `alert` (at risk, nothing lost yet), `warning`, and `info`, an expected state still within its budget, shown so the operator knows it is in progress. Rows are ordered by severity, then by rule in the table's order (what already broke actors first, what may lose state last), then newest `since` first. A row's `since` is the newest change among what it covers, a lower bound on how long the condition has held; the thresholds below are measured the same way.

| Rule | Row | Severity | Needs |
|---|---|---|---|
| `crashedActors` | One row for every crashed actor, grouped by template and by crash message, naming the latest. A template group whose crashes are all memory-limit kills (the worker's "killed for exceeding its memory limit") carries `cause: memoryLimit`; when every crash is one, the step names the remedy: create a template with a higher memory limit, move the actors to it (`kubectl ate update actor --template`, since a template can't be edited) and revert them (`kubectl ate revert actor`), the two commands in that order as `command` and `thenCommand`. Copied from the workspace, a `kubectl ate` command that changes an actor (revert, update, resume, suspend) carries `--kubeconfig` and `--context` for the cluster on screen on a local Radar, and a `<context>` to fill in where Radar can't know the reader's (in-cluster, Hub); in every mode it carries `--endpoint` when Radar reads Substrate anywhere but the `ate-system/api` Service kubectl ate port-forwards to (a saved direct endpoint, or `substrate.api.endpoint`). A snapshot restores memory only under the template it was taken under, so they resume from their volumes | Critical | Actors |
| `noMatchingPool` | A template whose worker selector matches no known pool. Says too when its golden snapshot cannot be built for the same reason | Alert: none of its actors can be placed, whether or not any is waiting | Templates, and every WorkerPool in the cluster read: a namespace pin or a caller limited to some namespaces reads only theirs, which can't show that none matches |
| `missingTemplate` | Actors naming a template Substrate does not have, one row per template. Substrate refuses to resume them (`FailedPrecondition`) without changing their state, so no other rule sees them | Warning | Actors, and every template read with none denied |
| `workerUnavailable` | A worker unavailable for more than 5 minutes. Substrate's controller marks a worker unavailable when its Pod stops being Ready with an IP, and available once it is again, so the row reads the Pod from Radar's cache: not Ready or no IP means Kubernetes is the cause; Ready with an IP means the controller has not marked it available (read its log); an unread Pod says both | Alert, with or without actors still assigned: the tone of the worker's own chip | Workers (Pods for the cause) |
| `workerDraining` | A draining worker that still holds actors or whose assignment coverage is incomplete. Draining only stops new placements; Substrate neither suspends nor moves the actors, and crashes any still assigned when the Pod is gone. The deadline is the worker Pod's `deletionTimestamp` from Radar's Pod cache, or, when Radar can't read it, the drain's start plus the 60 minutes Substrate gives worker Pods | Info until the deadline; warning after it | Workers, actors |
| `workerRestarting` | A worker whose registered epoch is ahead of the observed one: its process restarted and Substrate has not yet reconciled the registration. When actors still assigned ran under the earlier process, their sandboxes are gone. Suspended actors keep their snapshots when the assignment is released. For actors that did lose their sandboxes, the row leads with them ("3 actors lost their sandboxes when … restarted"), links to them (`/actors?worker=<pod>&impact=restarted`) and gives phase-specific recovery steps | Critical when actors lost their sandboxes; otherwise warning | Workers (actors for the loss) |
| `poolShort` | Fewer workers take actors than the pool wants: active workers from Substrate when every worker was read, else ready worker Pods from Kubernetes. A partial worker list (capped, or partly denied) proves a free slot it saw but never a shortfall or a full pool; placement then carries `complete: false`. Also raised from Prometheus alone: Substrate's own capacity alert condition held for 5 minutes (`workerShortfall`), or no schedulable worker of a known class (`noSchedulableWorkers`) | Warning; critical when none takes actors and the pool is not still converging (pending, resolving, scaling, or under 5 minutes old), or when Prometheus counts no schedulable worker | WorkerPools, workers or Prometheus |
| `poolFull` | No active worker in the pool has a free actor slot, from a complete worker read, or (Prometheus) no Substrate API server sees one. Slots only: CPU and memory are `poolNoRoom`'s. A pool short of workers reads `short`, not full | Warning | Workers or Prometheus |
| `poolNoRoom` | The pool's active workers have free actor slots, but none has the CPU or memory left for an actor of any template that can run on it (capacity `noRoom`), using the live worker labels and each worker’s default runtime overhead for a fresh actor. The reading names what binds and, when one dimension alone blocks every template, the most a worker has unbooked against the smallest booking. The step: add workers, or recreate the templates with lower limits; where kagent sessions run on those templates, lower kagent's `config.runtimeDefaults.cpu` and `.memory` instead, which set every agent's limits | Warning, as `poolFull`: nothing new is placed, nothing is lost | Every worker and every template read |
| `stuckTransition` | Actors resuming, suspending, reverting or deleting for more than 5 minutes, one row per state, saying which worker each waits on | Warning | Actors |
| `goldenSnapshotFailed` | A template whose golden snapshot failed (its golden actor, named the template's UID in its atespace, is this row's, not `crashedActors`', and its page points here), so new actors not seeded from a tag start from a cold boot, not a prepared snapshot. Substrate does not retry, and templates are immutable, so the step is to recreate it, with a higher memory limit when the golden actor was killed for exceeding it (the template's `golden.cause` is then `memoryLimit`). When its actors were killed over the same limit too, the template page gives one plan in the crash callout, which leads: recreate the template with a higher memory limit, move the crashed actors to it, then revert them. The reading drops Substrate's reason code (`GoldenActorCrashed:`) | Warning | Templates |
| `nodeUploadsOverdue` | A node whose atelet counts snapshot uploads past their deadline (Prometheus), by band (1–5m, 5–15m, over 15m), with the oldest state not yet stored. atelet's clock runs across suspend and resume, so it covers actors the API-only rule below cannot | Alert; critical when the node is NotReady or gone | Prometheus and a node running workers |
| `uploadOverdue` | Suspended actors whose newest snapshot is still pending upload and that were last updated more than 10 minutes ago, broken down by the node holding the files. Radar's threshold on the actor's last change, not Substrate's upload deadline | Alert however long it waits; critical when such a node is NotReady or gone | Actors (Nodes for the escalation) |

Prometheus verdicts are read for the pools the caller read as WorkerPools and, when the caller may read Nodes, the nodes running workers; `service` on the workspace says whether they were read and why not; `collecting` there means the first collection has not answered yet. Each row carries a title, Radar's reading (its first sentence is the cause or what is at risk, with any qualifier, and is all the Overview shows; mechanics such as epochs follow it, under Details), a next step (one action, at most 25 words), the `command` that runs it when one does (and `thenCommand`, run after it, when the step takes two), its subject and related links, how many things it covers, and up to 20 sample actors. A row covering several actors writes `<name>` and `<atespace>` in its command. On an actor's page, `ActorAttention` returns the rows that cover that actor, judged on the fresh read, with the command filled in and the crash step following that actor's own crash message. Readings never embed a clock time: deadlines and times are fields, which the UI formats.

Worker rows (`/workers`, the pool page) carry `workerState` when the worker is draining, unavailable, or active with a registration Substrate has not reconciled (`reconciling`), with how many actors are still assigned and how many lost their sandboxes when actor coverage is complete. Partial or unread actor lists leave both counts unknown. The restart and drain findings qualify any actors they did see. The recovery steps offer revert from running, crashed or suspended with a local copy of the last assigned generation. A revert already in progress gets wait guidance. The drain can offer suspend from running or suspending. A pool's readiness is counted from the worker Pods Radar's cache holds in namespaces where the caller may list Pods (`kubernetes.pods`: created, ready, terminating); `status.readyReplicas` is cited only where it disagrees. The memory-limit step on an actor's page follows the snapshot its revert keeps: on a new template, a snapshot stamped with the old one restores its volumes only, an unstamped root-filesystem snapshot its saved files, and with none the actor boots fresh.

### kagent sessions

kagent 1.x runs each chat session as one Substrate actor named `session-<session UUID>`, and runs its lifecycle itself: before any operation it checks the actor's UID and template, and it treats an actor moved to another template as lost, after which the session can only be deleted (kagent's `observeCrash` and `RevertSession`). On a cluster that serves kagent's API (`api.kagent.dev`), Radar marks actors with that name as kagent sessions (`kagent: {sessionId}` on the actor, set at read time from the name; it says kagent's naming, not which Agent the session belongs to), and no step offers `kubectl ate update actor --template` or `kubectl ate revert actor` for them: the crash rows, the template groups (`kagent: true`), the actor page, a lost sandbox after a worker restart and the memory-limit kill from the worker's log all say to recover the session through kagent: its `SessionService/RevertSession` call, which restores a crashed actor's last snapshot and marks the interrupted turn failed (valid only once Substrate marks the actor crashed; kagent 1.0.1 has no button or CLI command for it, later versions add Recover on the chat), or deleting the chat in kagent ("Stop active turns and delete"), which always works. Checked live against kagent 1.0.1: after `kubectl ate update actor --template`, `RevertSession` answers "runtime Actor identity or template changed". A memory-limit kill also says the session keeps the template it started with, so it may be killed again, and that kagent sets every agent's memory in its Helm value `config.runtimeDefaults.memory`. The marking holds on every read: the shared snapshot and the direct reads of one actor (its page, its logs, an exact-name search). Where kagent sessions crash beside other actors, the fleet row keeps the revert for the others and adds that kagent sessions recover in kagent. A template group's command runs for every actor in it, so a group that holds any actor kagent runs offers no command (`kagent: true`), and its step adds kagent's for those actors.

kagent also names the actor of a standalone sandbox `session-<UUID>`, under a template named `sandbox-<40 hex>`. A sandbox has no chat and no `RevertSession` (kagent 1.0.1's SandboxService creates, gets, lists, suspends, resumes and deletes), so Radar marks it `kagent: {sessionId, sandbox: true}` from its template's name, and its steps say to delete the sandbox through kagent's SandboxService and create a new one, never to move or revert it with kubectl ate.

What a worker's state means for an actor on it, `workerImpact` (`unavailable` with the Pod's `podState`, `draining` with the Pod's `deadline`, or `restarted`), is on the actor page, on every row of `/actors`, and on each worker's assigned actors in `/workers` and the pool page.

## API

Routes are registered in `internal/server/server.go` and advertised by the `substrateWorkspace` capability, so Radar Hub asks only a Radar that serves them. All are read-only except `PUT /connection`. "API tier" means the route needs Substrate's API: a request the gate refuses answers 403 `sharedRadar`, `apiDisabled` or `mintDenied`; a tier that is not connected answers 409 (`notConfigured`, `targetChanged`, `settingsFile`, `contextChanged`) or 503 with the code. A bad `PUT /connection` body is 400 `invalidSettings`; an unreadable worker Pod log is 502 `logsUnavailable`.

| Route (under `/api/substrate`) | Returns | Gate |
|---|---|---|
| `GET /status` | Whether WorkerPool is served, Service `ate-system/api` (found, when the caller may read Services there), the API tier, `coverage.pools`, `canConfigure`. Never waits for a first read: it answers `connecting` | Connected to a cluster. Refuses API access without sign-in, caller proof, or when the operator disables it |
| `GET /connection` | Discriminated `view: local` (saved settings or null, saved, targetChanged, current target, revision) or `view: managed` (enabled, readsAs, endpoint, serverName, trust source, Helm keys; atespaces only when connected). Both carry sharedPrincipal and this caller's APITier as access | Every mode; refused callers never reach a mint or API cache |
| `PUT /connection` | `{target, revision, settings, confirmDestination?, action?: "save" \| "reconfirm"}`; identity `none` removes the entry. 409 targetChanged/conflict/confirmDestination; 400 invalid settings; 413 over 16 KiB; 502 failed isolated probe keeps the old settings and active connection | Private local only: an in-cluster Radar or Radar Hub answers 403 `operator_managed` (its settings are Helm's), a local Radar on a shared listener 403 `sharedRadar`. | `GET /workspace` | Fleet summary (including actor and template attention counts), Needs attention, `checks`, `notAssessed`, actor states, pool rows (with Prometheus verdicts), `service`, atespaces, per-kind coverage | WorkerPools as the caller everywhere; the API parts only where the API is read |
| `GET /actors` | Actor rows (a crash whose message Substrate's worker writes for a memory-limit kill carries `cause: memoryLimit`, which the list shows as a short label, the message on hover), `total`, per-state `counts` and `attentionCount` (before `state`, `attention` and paging), `coverage`, `workerCoverage` for the worker-derived readings, and `sources` | API tier |

| `GET /actors/{atespace}/{name}/logs` | The actor's lines, from its worker Pod or the node it last ran on ([Where each value comes from](#where-each-value-comes-from)); `source` (`all`, the default, or `containers`, `lifecycle` or `worker`), `container` (not with `lifecycle` or `worker`, whose lines no container emits), `tailLines` (default 500, at most 5,000) | API tier, plus the caller's access to the worker Pods' namespace and to their logs. **`/actors` filters.** All combine.

- `state`: one or more reported actor states, comma-separated (an unknown state is 400).
- `attention=1`: select reported crashes, actors on unavailable or restarted workers, and stuck transitions. The count uses the same predicates as attention-first ordering.
- `atespace`: one atespace. When the shared read does not hold all of it (partial, or capped), Radar reads that atespace directly, under the same 50,000-actor budget, and `sources` says `atespace`.
- `template` and `pool`: `<atespace>/<name>` and `<namespace>/<name>`, or a bare name to match it in any atespace or namespace.
- `worker`: a worker Pod name or Substrate's worker name.
- `node` with `nodeHas`: `running` (the actor's worker is on that node) or `localSnapshot` (its newest snapshot is not durably stored and its files are on that node, so losing the node loses that state). `node` without one of them is 400.
- `q`: a case-insensitive substring of the actor's name, within what was read. When `atespace` is set and that atespace's direct read is itself capped, Radar also looks the exact name up with `GetActor` and adds it (`sources` gains `actor`).
- `impact`: `unavailable`, `draining` or `restarted`, the actors whose worker's state means that for them (`workerImpact.kind`); anything else is 400.
- `sort`: `updated` (default, newest change first), `attention` (crashed, then on a worker that is unavailable or restarted under them, then stuck past 5 minutes, longest waiting first, then the rest, newest first) or `name`; anything else is 400.
- `limit` (default 100, clamped to 1–1,000) and `offset` (default 0, clamped to 0–50,000). A value that isn't a number takes the default.

## Testing

`make substrate-demo` (read `scripts/substrate-demo/README.md` first) runs a fake Substrate API server on this machine against real WorkerPools and worker Pods in an existing cluster. It is not a kind cluster: the context defaults to `radar-test-nonprod` (`--context`). It serves Substrate's real wire protocol with deterministic data: 1,293 actors in four atespaces, and one scenario for every Needs attention rule, plus a limited token that is denied one atespace, and injected faults (`unavailable`, `unauthenticated`, `latency`). Open **Settings → Agent Substrate**, then enter the endpoint settings the script prints.

Unit tests: `pkg/substrate/*_test.go` (rules, derivations, log filtering), `internal/substrate/manager_test.go`, `internal/server/substrate_workspace_handlers_test.go` (gates, coverage, shared Radar), and `web/src/components/substrate/*.test.tsx`.
