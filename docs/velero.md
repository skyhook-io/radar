# Velero views

Radar's Velero views answer two questions the per-kind pages cannot: **are the schedules still producing good backups**, and **where do the backups go**. They do not answer whether a namespace is protected or whether a backup would restore: those need the coverage model, which is not built.

## Where it lives

| Screen | Route | Answers |
|---|---|---|
| Overview | `/velero` | Is Velero working: the server, schedules, newest successful scheduled backup and storage in one line (each label and value opens its list), then what **Needs attention**, grouped by server, schedules, storage, and backups and restores (each row its title, the object it is about, Radar's reading, then Velero's message folded last; the runs an unavailable location made Velero reject are links), then **Coverage**, information that never counts toward the attention badge: the namespaces the caller can see that no schedule's template selects (`includedNamespaces`/`excludedNamespaces`, matched as Velero matches them: an empty or `*` list is every namespace, entries are glob patterns, exclusions win; any schedule counts whatever its state or installation, and Kubernetes' own `kube-*` namespaces and Velero's are not listed; unknown when the schedules were read in part or under `--namespace-scope`), and the paused schedules, which submit no backups until resumed; then a **Schedules** table: each schedule's state, newest success, next run, where it writes (and whether that location is available) and how long its runs are kept (the schedule's `spec.template.ttl`, else "server default", which is also what an explicit zero such as `0s` means: Velero's backup controller substitutes its default for a zero duration, and the reading's `ttl` is then "", always sent; never read off a run, whose object backup sync may have recreated), so a healthy installation shows its evidence |
| Schedules | `/resources/schedules?apiGroup=velero.io` | Every schedule read against Velero's controller: when it runs in plain words ("Every 2 minutes", "Weekly on Sunday at 2:00"; the cron beneath, and the zone in the header or under it, said as "UTC — the Velero server's time zone"), its state, next run, last run (the newest run Velero keeps, with its newest success when that run wasn't one; when Velero last submitted one when no run is kept or read; **Never** when it submitted none), **Stored in** and **Kept for**, named as in the Overview's table |
| Storage locations | `/resources/backupstoragelocations?apiGroup=velero.io` | Each location's availability (and, when unavailable, why in plain words; Velero's message on hover), whether it is the default (a note under its name), validation, a failed validation as "Last checked 12s ago — failed", the backups targeting it (completed ones marked **not restorable** while the location is unavailable, the reason on hover) and the schedules writing to it |
| Backups | `/resources/backups?apiGroup=velero.io` | Every run, newest first, in-progress runs included, with **Failed** a segment away: outcome and, for a failed, rejected or partially failed run, why; items, errors and warnings, where it is stored (and whether that location is available) and when it expires. Run names in the lists and tabs are cut in the middle, keeping the end of their timestamp (`nightly-2026…41210`) |
| Restores | `/resources/restores?apiGroup=velero.io` | Every restore, newest first, with **Failed** a segment away: outcome and why it failed, the backup it came from, the namespaces it restored into (said as on its page: the included namespaces with each mapped one's destination, or every namespace in the backup; **Nothing — rejected** for one Velero rejected), errors and warnings |

**Narrow screens.** Below 1280px every Velero table folds its secondary columns into the cell they qualify, so no column is clipped at the right edge down to 1024px: a run's duration, items, location and expiry go under Started, its errors and warnings (only when there are some) under its outcome, a restore's backup under its name; a schedule's cadence under its name and its retention under Stored in; a location's three backup counts share one column. Names and namespaces in the tables and reason lines wrap only between words, never at a name's hyphen; a name wider than its column is cut with an ellipsis, whole on hover.
| An object's page | `/velero/<backups\|restores\|schedules\|backupstoragelocations>/<namespace>/<name>` | See [Pages](#pages) |

**In the sidebar: Backups, under Integrations.** Velero is one row in the Resources sidebar's **Integrations** block (under Favorites, above the kind categories), named for its job, **Backups**, with "Velero" beneath. The row's badge counts the rows Needs attention lists (issues the server capped still count, from the total it sends), reading ≥N over a kind read only in part and unknown (–) for a zero there. Opened, it lists **Overview**, **Backups**, **Schedules**, **Restores** and **Locations**; each list's badge counts the Needs attention rows about its kind (`veleroScreenCounts`), so they add up to the total less what belongs to no list (a stopped server, capped issues), and the Overview row has none. The four lists are the Schedule, BackupStorageLocation, Backup and Restore kinds' lists, Radar's own tables rather than the generic one (the Backup and Restore lists keep a name search and Create), so a schedule is never seen without its reading; the sidebar filter finds each by its kind name too. Velero's other kinds, the request kinds among them (a failed DeleteBackupRequest is where Velero says why a backup was not deleted), are folded under **Other kinds**. One integration is open at a time: it opens when one of its screens or kinds is on screen and stays open while the user looks at other kinds, until another integration opens. The Overview's status line links to the Schedule and storage-location lists. A Radar without the views, or whose capabilities could not be read, keeps the generic tables; on the first capabilities load the page waits rather than flashing them. Rows open the resource drawer, which leads with the object's page Overview, as CloudNativePG's drawer does: **Overview** (the page's banners and At a glance, unframed; a tab link such as **All N runs →** or **Restores →** opens that tab on the object's page) and **Spec & status** (the kind's renderer); the drawer's **Open full view** opens the object's page.

**The namespace filter does not apply.** Velero keeps its objects in its own namespace (`velero`, `kommander` on NKP, or wherever it was installed), while the filter selects application namespaces; applying it would empty the views. Every kind is still read only where the caller may list it, Radar's `--namespace-scope` still bounds the request (every Velero route answers 403 for a namespace outside it, before reading or creating anything), and a namespace the caller did not name is never reported as denied. A caller who cannot list a kind cluster-wide is checked only in the namespaces where Radar holds objects of that kind (its watched namespaces when Radar itself watches namespace by namespace), so the cost does not grow with the cluster and does not depend on Radar listing Namespaces; such a caller's coverage always reads partial, so it never shows whether Velero exists where they cannot look. The header's namespace picker is disabled on the Overview, the four lists and every object page, with a tooltip saying the filter doesn't apply; the page itself adds no line about scope. More than one installation shows installation chips, and a Radar limited to one namespace (`--namespace-scope`) says so under the title.

## Pages

Each Backup, Restore, Schedule and BackupStorageLocation has a page at `/velero/<plural>/<namespace>/<name>`, Radar's detail view framed by Velero: the title line starts with where the object lives (`Velero / Backups /`), which names the kind, so there is no kind chip, and a long name is cut (whole on hover) rather than pushing the header onto two lines, keeping at least 12rem while the badges beside it wrap among themselves; the page pins the Kubernetes context in `ctx` (after a context switch it says the object is not in the new one rather than opening a same-named object), and the sidebar highlights its kind, as its list does. Velero objects linked from a page open on their own pages; anything else opens in the drawer. **Overview** is a composed summary led by what Radar has for the object, as banners: a schedule's or location's reading when it needs attention (a schedule that cannot run, is late or held; overdue validation), which the workspace carries as readings rather than issues, then Velero's issues for it (its own, or a location's issue that names it among the runs it rejected). Each banner has a plain title, Radar's reading, the cause, one **Next step** line (the Issue's own action; else what its message means, such as "Create the bucket, or point the storage location at an existing one"; else the step for its kind of fault) and, for an issue, **See in Issues →**. When the Velero workspace is not read, or holds nothing for the object (it keeps the newest 50 issues per installation), the detail view's operational issues lead instead. The drawer shows the same Overview, with the renderer behind its **Spec & status** switch. **Spec & status** is the kind's renderer. A tab whose list holds failed runs carries a red dot (a schedule's **Runs**, a location's **Backups**); a backup's **Restores** tab carries their count.

| Page | Overview | Its own tab |
|---|---|---|
| Backup | **Outcome**: the badge, when it finished and how long it took, items backed up, errors (red) and warnings (amber), and the control that fetches the messages behind them, always here; a rejected run, or one that failed before it started, reads **Backed up: nothing** with Velero's reason instead, and shows no retention or restore row. **Namespaces**, as declared (and whether resource or label filters narrow it; `*` in an include list is everything, while `*` in an exclude list drops that whole scope and narrows it; the exclusions Velero writes into every processed spec itself, the CSI snapshot kinds on a backup and the kinds it never restores on a restore, do not count); volume snapshots and plugin operations when Velero counted any; where it is stored and whether that location is available, missing (only when the locations were read in full) or unread; how long it is kept (past its retention, Velero deletes it at its next garbage collection); the schedule that made it, or **On demand**. **Restore**: **No** with the reason where that is certain (it failed, has not finished, is being deleted, or its location is missing or unavailable: Velero restores only Completed or PartiallyFailed backups and refuses an unavailable location), otherwise **Restored before** with the newest restore from it that Velero finished (Completed or PartiallyFailed), its outcome and age, and **Not verified** when there is none, since Velero never tests a restore | **Restores** made from it (`spec.backupName`), with where each restored into |
| Restore | **Restored into** first: the namespaces it selects, as declared (none means every namespace in the backup), a mapped one as `a → b` (unmapped namespaces keep their names; an excluded namespace's mapping does nothing), each destination a link; a rejected restore reads **Restored: nothing** with Velero's reason instead; the outcome with its warnings beside it and the items processed (Velero's counter includes items it skipped or failed, so not "restored"); the backup it came from; the policy requested for existing objects; its errors and warnings | — |
| Schedule | One **At a glance**: when it runs (the cadence in plain words where Radar can say it, with its zone and the cron beneath), the last success (and whether the newest run since then failed), the next run (and why, when the schedule is not on schedule and no banner above already says so; **None** when it has none), the ten most recent runs as dots, newest first, each opening its backup, and **All N runs →** to the Runs tab; what it covers, as declared; where, and whether that location is available; how long each run is kept; the runs Velero keeps (`schedule.runs.kept`) by outcome, said as a lower bound when the read was partial or capped. A schedule Velero never submitted a run of reads **Never** for its last success, not "None kept" | **Runs**: every run Velero keeps (by `velero.io/schedule-name`, filtered on the server), newest first with **Failed** a segment away, with why each failed, duration, items, errors and warnings and expiry |
| Storage location | Availability, and when unavailable why in plain words, with Velero's message folded under it; last validation against its interval ("Last checked 49s ago — failed" on an unavailable location: Velero stamps every attempt), and the last sync attempt (`status.lastSyncedTime`); default ("set on this location", or a link to the location that is the default); access mode; provider and bucket (`s3://bucket/prefix` for AWS, `gs://` for GCP); the Backup objects that name it, as "48 backups · 30 completed · 16 expired · 2 failed" (completed: completed and inside their retention; not what is in the bucket), and on an unavailable location that none of them can be restored while it is; the schedules writing to it | **Backups** naming it, newest first, with **Failed** a segment away and the failed count in the subtitle; the date column is **Finished**, apart from the Completed outcome |

Runs and stored backups are what Velero still keeps: each is deleted once its retention passes, so neither is a full history.

## Back up now

**Back up now**, in the Schedule drawer's header with the other actions, creates a Backup from the schedule's template, exactly as `velero backup create --from-schedule` does (`pkg/velero.BackupFromSchedule`): the template as its spec, the template's labels (else the schedule's) plus `velero.io/schedule-name`, the schedule's annotations except kubectl's last-applied, an owner reference when the schedule sets `useOwnerReferencesInBackup`, and the name `<schedule>-<UTC timestamp>`. The confirmation shows what it backs up (the template's namespaces, and whether resource or label filters narrow them), where it is stored and how long it is kept; a toast names the new backup, which also appears among the schedule's runs.

- **Unavailable when it would not back up now.** Disabled, with the reason as its tooltip, for a schedule that cannot run, when Velero runs with backups disabled (restore-only), and while the Velero server is stopped (a Backup created then waits in `New` until the server starts). When the server's Deployment can't be read it stays enabled. The server also refuses (409) when it is known stopped or its backup controller is disabled by `--restore-only` or `--disable-controllers` containing `backup`; disabling only `schedule` does not disable an on-demand Backup. The activity response exposes `backupsDisabled` beside `serverStopped`.

- **It is one of the schedule's runs.** Radar lists it among the runs, and while it is new or in progress Velero does not submit the schedule's next run (the controller's hold covers only those phases, not queued or finalizing ones); the confirmation says so.
- **As the caller.** The schedule is read and the Backup created with the caller's identity, so the apiserver enforces `get schedules` and `create backups`.
- **Bound to what was reviewed.** The confirmation freezes the schedule it shows. The request carries that `resourceVersion`, and a schedule edited since is refused (409); the dialog disables itself if the schedule changes while open.
- **Once per confirmation.** The confirmation chooses the name (`<schedule>-<UTC timestamp>`) and a `submission` ID when it opens. Requests carry `{resourceVersion, name, submission}`; `submission` must match `^[A-Za-z0-9-]{8,64}$` and is stored as the Backup annotation `radar.skyhook.io/submission`. A retry returns an existing Backup only with that annotation, even if the schedule was edited since. Another confirmation in the same second, or a controller-created Backup with the same name, gets 409: "another backup was created with this name; review again".
- **Refused when it would fail:** a schedule whose name does not fit a label (409; the button is disabled).
- `POST /api/velero/schedules/{namespace}/{name}/backup`, behind capability `veleroBackupNow`.

## Delete backup

A Backup object is not the backup. Deleting it leaves the backup's files in the bucket and its volume snapshots with the provider, and Velero's backup sync recreates the object from the bucket. Velero deletes a backup through a **DeleteBackupRequest**, as `velero backup delete` does, so that is the only delete the UI offers for one: the Backup page and drawer header's **Delete backup**, in place of the generic Delete, and bulk delete is not offered for Velero backups. Deleting the object stays possible as a low-level operation (`DELETE /api/resources/...`, MCP `delete_resource`), whose preview says what it does not delete and how to delete the backup through Velero.

- **What Velero deletes:** the backup's files in its storage location, its volume snapshots and uploaded volume data, the Restores made from it, then the Backup object. The confirmation says so and asks for the backup's name.
- **Refused when Velero would refuse:** a backup still running (`InProgress`, `WaitingForPluginOperations*`, `Finalizing*`, the phases Velero's backup tracker holds), a storage location that is read-only or not Available, a stopped Velero server (nothing would be deleted until it starts), or a Backup whose `spec.storageLocation` has not been assigned yet. When the location can't be read, Velero's own refusal is reported once it processes the request.
- **Bound to what was reviewed:** the request carries the backup's UID, and a backup recreated under the same name is refused (409). A DeleteBackupRequest names a backup only by name, so this protects the submission, not Velero's later processing: a backup deleted and recreated under the same name before Velero picks the request up would be the one deleted.
- **Reuse an open request:** the server lists DeleteBackupRequests in the namespace by `velero.io/backup-name=ValidLabelValue(name),velero.io/backup-uid=<uid>`. POST returns the newest open (not `Processed`) request if there is one; otherwise it creates one with `generateName: <backup>-`, as the CLI does. Concurrent submissions can still create two requests before either list sees one; Velero serializes deletion.
- **Followed wherever opened:** GET reads the newest matching request and when it was made (`created`). The page and drawer show waiting and deleting in the header. A settled deletion that left the backup (refused, failed: some data may already be gone, or unknown) is a **Deletion** row in the At a glance, on the page and in the drawer ("Refused 2h ago — at the time, storage location `nowhere` didn’t exist; nothing was deleted", the location's name a name and, when it exists now, a link; Velero's text on hover), since Velero keeps a processed request for a day and a header chip would read as the backup's status. A refusal is about the request: the location may have been changed since, so the row says how it was then. Failure toasts appear once per request, only for a request sent from this browser. The page's gone state covers completion. A 4xx stops polling; error with no data reads unavailable, while a refresh error keeps the last reading. A missing request while the Backup remains cannot distinguish a cleaned-up old request from no request ever made.
- As the caller: `get backups`, `list deletebackuprequests` for both lookup and submission, and `create deletebackuprequests` for a new request. `POST /api/velero/backups/{namespace}/{name}/delete` `{uid}` and `GET /api/velero/backups/{namespace}/{name}/deletion?uid=`, behind capability `veleroDeleteBackup`. GET includes `request` and `created` when one exists; neither response echoes the UID. A Radar without the capability shows no delete for Velero backups.


## Data

- `GET /api/velero/workspace`: every installation the caller can read. Readings, not objects; every time is absolute, with `observedAt` saying when the readings were computed.
- `GET /api/velero/schedules/{namespace}/{name}/activity`: one schedule with its recent runs, for its Overview and header. 403 outside the namespace pin before discovery or inventory reads, or without `list schedules` there; 404 when it does not exist.
- `GET /api/velero/runs/{backups|restores}?namespace=`: every Backup or Restore the caller can read, newest first (at most 5,000, with the total). `schedule=` filters Backups by `velero.io/schedule-name`; `backup=` filters Restores by `spec.backupName`. Filters run before sorting and capping, and `total` counts the filtered set. Each run carries `reason` from `status.failureReason`, else `validationErrors` joined with "; ". A Restore also carries `namespaceMapping` and, always (empty for every namespace), `includedNamespaces` and `excludedNamespaces`. Lists are read through the same per-kind access as the views, so a reader of Velero's kinds alone needs no Pod or Deployment access; `coverage` says what it covered, and the lists and tabs show lower bounds (≥N) over a partial read. Behind capability `veleroRuns`.
- Capability flag `veleroWorkspace`. An older Radar shows a "needs a newer Radar" note and the kind lists keep working.
- Rules: `pkg/velero` (pure, no Kubernetes calls). Service: `internal/velero`. Server adapter and handlers: `internal/server/velero_workspace.go`.

## Where each value comes from

| Value | Source | When it cannot be read |
|---|---|---|
| Schedule state | The Schedule, its Backups (by `velero.io/schedule-name`), and the installation's server configuration, against Velero's controller (`schedule_controller.go`, v1.18.2) | Backups unread: runs are `unknown`, and a missed run reads **late or held** |
| Next run | `cron.Next(max(lastBackup or creationTimestamp, lastSkipped))`, robfig/cron v3 as Velero uses it | The zone below decides whether it is exact |
| Zone | `CRON_TZ=`/`TZ=` in the expression; else the Velero server Deployment's literal `TZ` (none set → UTC) with its rollout complete | Inferred only from the controller submission matching `status.lastBackup` (name timestamp minus lastBackup, rounded to 15 minutes; creation within a minute of lastBackup): an estimate, prefixed `~`. Newer UTC-named CLI and Back up now runs never supply the zone. Nothing: UTC, marked unknown |
| Newest run, newest successful run | The schedule's Backups Velero still keeps (TTL deletes older ones) | "Unknown" when the namespace's Backups are unread; never "none" |
| Default storage location | A location with `spec.default`; else the server's `--default-backup-storage-location` (an explicitly empty flag means no default, and a backup naming no location fails) | "unknown" when neither can be read |
| Validation interval | `spec.validationFrequency` (> 0; `0` disables); else the server's `--store-validation-frequency` | No overdue verdict |
| Backups targeting a location | Each Backup's `spec.storageLocation`, which Velero fills when it first processes the backup | A backup without one is "not yet assigned", never counted under today's default |

An `@every` schedule adds a fixed duration to its anchor, so its times are exact whatever the zone.

`server.replicas` counts non-terminating pods, including Pending and CrashLoop; `server.readyReplicas` is a separate count whenever the Deployment was read, including during rollout. Zero ready replicas with replicas present means not ready, not proof that controllers have stopped. `Down()` and stopped-server Issues still use replicas==0. `server.backupsDisabled` is present (true or false) only when flags are known; it is separate from `schedulingDisabled`.

Server configuration counts only when its effective value is known: a `TZ` from `envFrom`/`valueFrom` or an argument built from `$(VAR)` leaves it unknown, and during a rollout the previous template may still be running, so nothing is taken from it.

## Schedule states

First match wins.

| State | When | Needs attention |
|---|---|---|
| Paused | `spec.paused` | No |
| Scheduling disabled | The server runs with `--restore-only` or `--disable-controllers=…schedule…` | No |
| Rejected | `FailedValidation` or `validationErrors` | Shown through its Issue (`ScheduleValidationFailed`) |
| Cannot run | Name longer than 63 characters: Velero writes it unshortened into a label, so every submission fails and Velero submits no runs (its last success reads **Never**) | Yes |
| Not validated | Phase is not `Enabled`; the controller validates on create | After 5 minutes |
| Unknown | Velero accepted a cron Radar cannot parse | No |
| Always due | The cron has no future time; Velero compares now against the zero time, so it submits a new run whenever the previous one has started | Yes |
| Skip pending | `spec.skipImmediately` is set; the controller moves its anchor on the next pass | No |
| Held | Due, and a run of the schedule is `""`, `New` or `InProgress` (the controller's skip rule) | When the run has not started for 10 minutes; a long `InProgress` run is the stalled-run Issue's |
| Late | Past the next run by 5 minutes, zone certain, Backups read, nothing holding it. Counts the scheduled times that passed; Velero does not catch up | Yes |
| Probably late | Past it, zone not certain: inferred zone by 2 hours, unknown zone by the cadence plus a day | Yes |
| Late or held | As Late, but the namespace's Backups are unread, so a hidden run may hold it | Yes |
| Possibly late | Past the estimated run within the uncertain margin | No |
| Due | Within the 5-minute grace | No |
| On schedule | Otherwise | No |

**A stopped server is named first, once.** When the Velero server Deployment can be read and has no running replicas (scaled to zero, or its pods cannot be created), it leads Needs attention, and its row names the schedules it leaves late ("3 schedules have missed runs: a, b and c"), which get no row of their own; overdue locations are not listed. A schedule wrong for another reason (cannot run, rejected) keeps its own row. An unready pod with replicas present does not count as stopped: readiness alone cannot say whether it processes schedules. A pod still terminating is not counted either; its controllers stop on SIGTERM, so it submits nothing new.

Storage locations need attention when **validation is overdue**: the interval is known and more than three intervals plus 5 minutes have passed since the last validation (Radar's threshold). An Unavailable location is already an Issue (`BackupStorageLocationUnavailable`).

The certain readings are also Issues, raised by the Problems surface from the same rules, so they reach `/api/issues`, MCP and Diagnose: a stopped server, and schedules that are late, cannot run, held or not validated, and overdue validation. One fault is one Issue: see [one fault, one issue](integrations.md#one-fault-one-issue). Estimates ("probably late", "late or held") stay readings here. See the Velero section of [integrations.md](integrations.md). These views keep showing their own readings, which need no Pod or Deployment access, and do not list those Issues twice.

## Issues on these views

The Velero Issues the Problems surface raises, computed by the same detector (`issues.DetectVelero`) over the objects these views read. A row therefore exists only where the caller could read its kind in that namespace, and a Velero-only reader with no Pod or Deployment access still sees them; the Problems surface, which scopes by namespace access, may show such a reader fewer. Nothing else in the cluster is scanned to produce them. At most 50 per installation are returned, with the count before the cap; a row from an unread namespace is never counted or named. An unavailable location's row names the runs Velero rejected because of it, which get no row of their own.

## Recent runs and run messages

A schedule's At a glance, on its page and in the drawer, shows the ten most recent runs the activity read returns as dots (outcome and age in the tooltip, each opening its backup), and **All N runs →** opens the schedule page's Runs tab, N being the runs Velero keeps.

A Backup or Restore's error and warning text is not on the object: **Show 9 errors and 3 warnings** asks Velero for its results file (at most 500 messages). On a page the button sits in the Outcome row. In the drawer it sits in the Overview's Outcome row too; on Spec & status, on a failed or partially failed run whose Issue the drawer shows, it sits inside that Issue's *What's wrong*, otherwise in Status. The list is grouped by scope (Velero, cluster-scoped, or a namespace) with counts, folds exact repeats, and messages that differ only in one object's identity written as one (`name=x`, or a slash reference like `ns/pod`; a bare or quoted word may be a reason and never folds), one error per failed item, so forty PVCs read as one line "× 40" with the names on expanding (the folding index is bounded: at most four identities a message and 512 KB in all, past which messages fold only exact repeats), and shows the first 10 rows with **Show all N** for the rest.

Downloads enforce the destination policy at dial time on the resolved IP, so a DNS change cannot bypass it. Link-local (`169.254.0.0/16`, `fe80::/10`), unspecified and multicast addresses are always refused. Loopback is allowed only in local mode with a loopback listener, for a laptop's object-store port-forward; shared listeners and in-cluster Radar refuse it. Private addresses remain allowed for stores such as MinIO. Downloads use no proxy and follow no redirect. A refusal returns 503 with a destination-policy explanation and no signed URL.

## Plain reasons

Velero passes the object store's and the network's errors through as it gets them. Radar reads the common ones as one plain line with a next step (`veleroPlainReason` and `veleroReasonNextStep` in `packages/k8s-ui/src/components/velero/reading.ts`) and keeps Velero's text a click or a hover away: a missing bucket, credentials that are wrong or cannot access the bucket, an object store Velero cannot reach, a run Velero marked Failed because its server restarted while it ran, and Velero's own refusals naming a storage location (unavailable, read-only, missing, or no default), said as "storage location" rather than BackupStorageLocation or BSL. They lead the Overview's and pages' issue rows, the storage location's page and list, and a failed run's reason in the lists. A message Radar does not recognise is shown as Velero wrote it.

## Schedule badges

A schedule's badge (lists, the page's title, the Overview's Schedules table) is its state, with three readings for a schedule otherwise on schedule: one **due** within its grace while the server runs reads **On schedule** (its next run reads "due now"), since Velero submits it on its next pass; one whose newest run failed, partially failed or was rejected reads **Last run failed**; and one whose zone Radar has not confirmed (inferred or unknown) reads On schedule in grey, not green.

The Overview's server reads **running** only when a replica is ready, and **not ready** when it has replicas but none is.

## Limits

- **Completed is not restorable.** "Completed, not expired" is what Velero reports; it does not say the data is in the bucket or that a restore would succeed.
- **An uncertain zone is not daylight-saving safe.** A weekly schedule at a local hour skipped by a daylight-saving change can exceed the uncertain margin and read "probably late". Readable Deployments avoid it.
- **An installation needs a storage location for its readings to become Issues.** The derived Issues are raised per namespace holding a BackupStorageLocation. Without one, every backup is already rejected and raised as such, but a stopped server there is shown only on these views.
- **Runs are matched by schedule name.** A recreated or edited schedule's older runs still count as its runs.
- **Velero 1.16–1.18.** 1.16 and 1.17 do not count an empty-phase run as holding; Radar does.

## Testing

`make velero-demo` freezes every phase with the controller scaled to 0, so schedules genuinely go late; `30-schedules.yaml` adds a held schedule and one whose name is too long. `./scripts/velero-demo.sh live` lets a running controller submit a schedule's runs and refuse the long-named one. See `scripts/velero-demo/README.md`.
