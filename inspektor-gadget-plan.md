## Premise (honest framing)

This is **two things at once**, and the plan says so: (a) a partnership/demo play — a credible, working integration to bring to the IG maintainers — and (b) a real capability bet: Radar's visibility ends at the API server, and kernel-level evidence (what's actually running, resolving, connecting) is the missing layer. The addressable audience is real but narrow today (IG installed; Linux nodes with BTF; not GKE Autopilot/Fargate) — AKS's supported add-on is the main installed base. We accept narrowness for the MVP because the demo goal dominates; Phase 2's install-recommendation card is the demand-discovery mechanism.

**Wrong version:** a generic gadget browser — Headlamp (and Microsoft's Headlamp-based AKS Desktop) already ships that. **Right version:** curated answers on the Pod page + MCP exposure. **Differentiation, stated precisely:** IG now has an official MCP server (`inspektor-gadget/ig-mcp-server`) and AKS's MCP server exposes IG too — so "MCP nobody has" is false. What nobody has is the *combination*: kernel evidence curated into the Pod-detail journey, aggregated into verdicts, and served from the same MCP surface as Radar's K8s-API tools (one tool call correlating both layers). The spike evaluates aligning with / reusing ig-mcp-server rather than duplicating their runtime layer — also a better partnership posture: they're already MCP-invested.

**Simpler-architecture check (evaluated, rejected):** folding this into the existing diagnose-runs abstraction. Rejected because diagnose is the AI-/consent-gated flow with a conversation lifecycle; Live Debug is direct, deterministic evidence-gathering. We reuse diagnose's *plumbing patterns* (run + SSE + server-side continuation, `internal/server/server.go:365-382`, `web/src/api/diagnose.ts:234-282`), and a later phase can let diagnose consume `pkg/igdebug` as a collector.

## Certain (verified, cited)

- IG clients speak gRPC to the `gadget` DaemonSet **through the kube-apiserver**: `grpcruntime.New(grpcruntime.WithConnectUsingK8SProxy)` + `SetRestConfig(cfg)` + `RunGadget(...)`, gadget = OCI image ref, pod targeting via `operator.KubeManager.selector` (IG repo `docs/api/_golang/grpc_kubernetes/main.go`). Latest IG: v0.54.1 (2026-07-14).
- The proxy leg is authorized by the apiserver **against the identity in the rest.Config** — so per-user enforcement requires per-user (impersonated) configs, same as Radar's MCP write path (`DynamicClientFromContext`, per CLAUDE.md security pattern). A SAR is a preflight opinion only.
- IG's own authorization is coarse: anyone who can reach the gadget pods' proxy/portforward subresource can run any allowed gadget against any workload on the node. Admins can restrict *which gadgets* run via IG's allowed-gadgets/digest restrictions (daemon-side policy), not *which workloads* may be traced.
- Gadget semantics (IG docs, v0.54): `trace_exec` = **new** execs only (cannot see already-running processes); `trace_tcp` = connect/accept/close (drops/retransmits are separate gadgets); `trace_dns` = separate query/response events, ordering not guaranteed (correlation is client work); `snapshot_process` / `snapshot_socket` = one-shot current state.
- Radar slots: SSE routes exempt from the 60s timeout via route groups (`internal/server/server.go:293,356,372`); detection pattern `TrafficSource.Detect` (`pkg/traffic/source.go:10`, `internal/traffic/caretta.go:108`); optional-prop renderer injection (`web/src/components/resources/renderers/PodRenderer.tsx:61-73`; `packages/k8s-ui/.../PodRenderer.tsx:93,836`); MCP `registerTools` + catalog CI test (`internal/mcp/tools.go:37-41`); `Recommendation`/`HelmChartInfo` for Phase 2 (`pkg/traffic/types.go:126-164`).

## Design decisions (Confident)

**D1. Consumption path: embed IG's Go gRPC runtime (`WithConnectUsingK8SProxy`), isolated behind `pkg/igdebug` interfaces.** Hand-rolling the datasource wire format + params + version negotiation is worse. Known-optimistic caveat: the abstraction will leak IG semantics; the spike must show the seam is real. Dependency weight, CGO, licensing, and cross-compile impact are explicit spike gates.

**D2. Snapshot-first MVP.** Three curated Pod-detail answers, but only ONE is a streaming session:
- **Processes** = `snapshot_process` (what's running *now* — one-shot request/response, no session, no SSE). Fixes the semantic hole that `trace_exec` can't see existing processes. `trace_exec` ("what's being spawned") becomes a fast-follow toggle.
- **Connections** = `snapshot_socket` (current sockets/peers — one-shot). Honest labeling: current state, not failure history; `trace_tcp`/`trace_tcpdrop` are fast-follows.
- **DNS** = `trace_dns`, the single streaming run (10/30/60s): the highest-value live diagnosis and the demo centerpiece.
This shrinks MVP surface to: one-shot snapshot endpoint + one bounded streaming run type.
**Snapshot completion (spike-verified):** the released snapshot gadgets emit one complete `datasource.TypeArray` packet but keep the gadget context alive. Subscribe with `SubscribeArray`, copy the complete packet, publish it as data-ready, then cancel/unload explicitly and finish bounded cleanup in the manager. The HTTP/MCP caller may receive the complete snapshot while the run remains `stopping`; it must not wait on the observed 6-8s remote teardown path. Do not use the per-row callback as a completion signal and do not add a quiet-period fallback for the three pinned gadgets. Snapshot requests execute as **manager-owned runs with a synchronous fast-path**: the run id is allocated immediately, the handler waits a short fast-path budget for data-ready, and past it responds `202 + runId` for polling while the manager continues (and owns cleanup — a cold OCI pull or client abort must never leak instrumentation). Snapshots live under the same D6 state machine, caps, startup deadline, retention, and terminal states as trace runs — "one-shot" is a fast-path, not a separate lifecycle. "One-shot" describes Radar's API shape, not an assumed IG behavior.

**D3. DNS aggregation is defined honestly.** IG v0.54.1 already emits response-side `latency_ns_raw`, rcode, answer addresses, nameserver, and Pod/Service-enriched endpoints. Treat those as authoritative and aggregate per name/type; do not duplicate query↔response correlation. Track outstanding queries on (DNS id, qname, qtype, transport, direction-normalized endpoints, container, bounded time window) only to report **unmatched queries** as their own bucket ("no response observed in window") — never claim "timeout" from absence. Coverage disclosures in every result: multi-packet DNS-over-TCP not reconstructed; DoT/DoH invisible; v0.54.1 does not expose usable event-loss telemetry for these gadgets, so Phase 1 reports `unmeasurable` and never claims "no loss." Radar's own `truncated` flag is separate and describes only result rows Radar actually omitted. Every result carries metadata: capture window, target (pod UID, container, node), event counts. No verdict without a denominator.

**D4. Targeting is node- and identity-precise.** At run creation: resolve pod → UID + node + container list + **runtime container ID**; require a container choice when >1 (default: honor `kubectl.kubernetes.io/default-container`, then fall back to the first app container, matching Radar's exec/log convention; switcher in UI); set the gRPC runtime's `ParamNode` so the gadget executes **only on the target node**; reject unless that node's gadget Pod is Ready. IG's KubeManager selectors are *name*-based and expose no Pod-UID/container-ID selector, so UID precision is Radar's job: filter rows on the pinned container ID and watch the pod's UID/node for the run's duration — pod deleted/recreated under the same name ⇒ run ends `partial` with reason.

**D5. RBAC: enforced by identity, not preflight — impersonation ships in the MVP** _(per sign-off 2026-07-19)_.
- **No-auth/local mode:** the kubeconfig identity runs the show — same as every other Radar operation; the apiserver decides.
- **Auth/multi-user mode (MVP):** every run/snapshot builds the IG runtime's rest.Config with the acting user's impersonation headers (same pattern as MCP writes via `DynamicClientFromContext`), so the apiserver — not a SAR preflight — authorizes the proxy leg per user. Run objects are owned by (user, context); stream/stop/result authorized against owner. Concurrency caps are per-user (fairness, no cross-user DoS).
- **Honest limit, documented:** impersonation gates *access to the gadget proxy*, not *which workload gets traced* — IG has no workload-level authorization (their 2026 security audit notes namespace blocking as unfinished). Access to the gadget namespace's pod proxy = ability to trace anything on the node; the security-posture doc says so explicitly and points admins at narrow grants + IG's daemon-side allowed-gadgets/digest restriction as the controls.

**D6. Run lifecycle is a real state machine.** States: `starting → running → stopping → (complete | stopped | failed | partial)`; snapshots may expose a frozen data-ready result in `stopping`. Server buffers events from t0 (SSE attach never loses the head); `GET /api/ig/runs/{id}` returns state + any frozen result (retained in memory, LRU-capped, dropped on context switch); caps: max duration 300s, max events + max bytes per run (excess → truncated flag), max concurrent runs total AND per-user. Capture duration is IG's instrumentation-live timeout after operators start, not request wall time; startup/OCI pull has its own deadline. Stop and context switch both cancel the manager-owned context and wait for bounded unload. **Disconnect rule:** browser SSE disconnect never cancels a run — only explicit stop, duration expiry, context switch, or TTL do; the manager-owned gadget context is the sole thing whose cancellation unloads instrumentation. Streaming route lives in the no-timeout SSE group.

**D7. MCP: ONE tool, shipped in MVP.** `inspect_pod_runtime(namespace, pod, container?, aspect: dns|processes|connections, duration?≤30s)` — snapshots return through the data-ready fast path while manager-owned cleanup continues; DNS collects synchronously with the tool's **own deadline** covering proxy setup + OCI pull + collection (`/mcp` mounts outside the 60s middleware group — `internal/server/server.go:668-674` — so the bound is ours to enforce). No image pre-pulling on the status path (a status read must not mutate); if startup exceeds the deadline, return the actual IG startup/pull error when available, otherwise a clear startup-timeout/retry error rather than guessing that an image is pulling. Result = the same `pkg/igdebug` summary types with **MCP-specific minimization**; DNS names are treated as sensitive-by-default and the default capture is 10s. (`snapshot_process` exposes `comm`, not argv.) Tool annotations: NOT pure read-only — it loads kernel instrumentation; annotate accordingly and say so in the description. Absent IG → crisp actionable message. Catalog + docs/mcp.md updated (CI-enforced).

**D8. Detection is tri-state and per-run re-checked.** `GET /api/ig/status` → `installed | not-installed | unknown`. `not-installed` requires proof: a *successful* cluster-wide service-identity search for the canonical gadget DaemonSet label (custom namespaces are supported, so absence from ns `gadget` proves nothing); any inability to perform that search (forbidden, partial) ⇒ `unknown`, never "not installed". Use a live typed-client list rather than assuming Radar's namespace-scoped informer contains the gadget namespace. Best-effort version (tolerates digests/mirrors/AKS auto-upgraded extensions — version string is informational, not a gate), gadget namespace discovery (default `gadget`, label-based fallback). No global "healthy" boolean — readiness is evaluated per target node at run creation with the acting user's impersonated config (D4/D5). Compatibility: pin library version; CI matrix = IG latest + latest-1 minor on kind; out-of-range deployed version ⇒ warning banner, not a block.

**D9. Gadget artifact policy.** The curated gadget images are pinned **by digest** per Radar release (not `:latest`, not floating tags); v0.54.1 pins are recorded in `inspektor-gadget-spike.md`. A `--ig-gadget-registry` flag overrides the registry prefix for mirrored/air-gapped clusters; when the daemon's allowed-gadgets/signature policy rejects our reference, surface IG's error verbatim with a doc link — no silent fallback to other refs. Digest bumps ride Radar releases and are owned like any dependency update. This is privileged-code supply chain, not a convenience knob.

## Build sequence

**Phase 0 — complete (see `inspektor-gadget-spike.md`):**
1. Run `trace_dns` + `snapshot_process` via the Go library against a target pod; confirm attribution and field shapes match the aggregator design; check whether pod UID appears on events; determine the snapshot completion signal (protocol-level, or calibrate the quiet-period) and confirm the instance unloads on cancel.
2. Verify node-scoped gadget load (not just server-side event filtering); verify cancellation unloads on explicit stop, run-manager teardown, and partial start. (Browser SSE disconnect deliberately does NOT cancel — D6; what must never leak is the manager-owned gadget context.)

4. Behavior under: denied OCI pull, allowed-gadgets restriction, gadget pod not ready on node, multi-container pod.
5. Write up concrete findings/questions as a short report (this becomes Nadav's first post to `#inspektor-gadget` Slack — **prepare it; do not post it**).

**Phase 1 — MVP:**
1. `pkg/igdebug/` — pure: client interface, run manager (state machine, caps, buffering), snapshot fetchers, DNS aggregator. Unit tests on aggregators with recorded event fixtures incl. malformed/unordered events, snapshot data-ready before teardown, per-user + total cap races, context-switch cancellation/unload, and retention.
1b. **K8s↔kernel correlation (the differentiator, in v1):** enrich `snapshot_socket` peer addresses against Radar's informer cache — with attribution honesty: an exact Service-VIP or Pod-IP match is stated as such ("peer is Service db/postgres" / "peer is pod postgres-0"), while path claims across NAT (VIP → which backend pod) are labeled *inferred association* unless IG exposes pre/post-NAT context (spike checks). This is what Headlamp's generic renderer cannot do and what justifies "curated"; without it we're a gadget viewer.

4. MCP tool + catalog + docs/mcp.md; redaction tests.
5. Frontend: `web/src/api/igdebug.ts`; `LiveDebugSection` (pure, in `packages/k8s-ui`, props-injected — additive props only, no breaking change to `@skyhook-io/radar-app`); host wrapper in PodRenderer; DESIGN.md tokens; empty/error/unknown states designed (incl. `unknown` ≠ "not installed" copy).
6. `scripts/ig-demo.sh` (kind + IG + fixture workloads chosen to exercise the *MVP* gadgets: long-running processes incl. an unexpected extra process for `snapshot_process`; listening + established connections for `snapshot_socket`; a pod with failing DNS for `trace_dns`; chatty-exec fixture reserved for the Phase 2 `trace_exec` toggle) mirroring `gitops-demo.sh`; visual-test; demo GIF.
7. kind-based integration test with an explicit allow/deny matrix: (a) impersonated identity *without* gadget-proxy permission is denied; (b) identity with the documented minimum grant succeeds; (c) revoking the grant flips the result without touching Radar's own service identity — proving apiserver enforcement, not header forwarding. The test also derives and documents the **complete minimum permission set** the embedded runtime needs (beyond `pods/proxy`: discovery/list/get used to locate the node's gadget pod).
8. Security-posture doc section (who can trace what; IG's coarse model; admin controls).

## Risks (visible, owned)
- IG Go library dependency weight / pin conflicts (spike gate, thin-client fallback).
- Aggregator correctness on unordered/partial event streams — fixture-driven tests, honest `unmatched`/`truncated` reporting.
- apiserver-proxied gRPC stability on flaky clusters — bounded runs + buffered results limit the blast radius.
- Narrow initial audience — accepted; Phase 2 card + partnership channel are the growth path.
- IG architecture docs are WIP — spike validates every load-bearing assumption; unknowns go to IG Slack early.

## Decisions (signed off 2026-07-19)
1. **Auth-mode:** build per-user impersonation in the MVP (D5) — feature works under auth from day one, operator-scoped by real apiserver enforcement.
2. **Install upsell:** detect-only MVP; recommendation card in Phase 2.
3. **Container default:** honor `kubectl.kubernetes.io/default-container`, then use the first app container, with a visible switcher.
4. **Naming:** "Live Debug".
